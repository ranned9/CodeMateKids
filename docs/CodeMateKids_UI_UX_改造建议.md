# CodeMateKids UI/UX 改造建议与实施规范

> **文档类型：** 产品界面与交互改造建议\
> **适用项目：** CodeMateKids（Windows Demo）\
> **整理日期：** 2026-11-20\
> **目标：**
> 在保留现有教学闭环与自研积木编辑器核心能力的前提下，借鉴成熟开源编程教育产品的界面组织方式，降低儿童使用时的认知负担，并改善桌面窗口适配与空间利用率。

------------------------------------------------------------------------

## 1. 总体判断

当前 CodeMateKids 已具备课程目标、预测、积木编辑、程序运行、结果反馈、AI
辅导和学习总结等完整教学环节。现阶段 UI
改造的重点应从"把功能放进页面"转向"围绕儿童完成当前学习任务组织页面"。

建议将原有三条修改意见落实为以下三个方向：

1.  **建立成熟产品参考基线：** 对 Scratch、Code.org Sprite
    Lab、Microsoft MakeCode、Blockly
    等项目进行有目的的界面拆解，优先复用成熟的信息架构、组件样式、状态反馈和交互范式，减少自定义设计成本。
2.  **重构儿童界面的信息层级：**
    一个页面优先突出一个学习目标、一项当前任务和一个主要操作。将技术状态、次要说明、扩展内容和低频操作收纳起来，避免多个区域同时争夺注意力。
3.  **重新分配窗口空间：**
    让积木工作区获得主要空间，课程说明、工具箱、运行结果和 AI
    辅导围绕工作区组织；按窗口宽度和高度调整面板的显示方式，避免固定尺寸造成拥挤或大量空白。

**核心原则：先保证孩子知道"现在要做什么、在哪里做、做完后看哪里"，再考虑页面能展示多少功能。**

## 2. 当前项目 UI 基线与主要问题

以下判断依据当前仓库中的
`README.md`、`frontend/index.html`、`frontend/css/app.css`、`frontend/js/views/`
以及 `docs/manual-checklist.md`。

### 2.1 当前页面结构

当前主页面包含以下区域：

  ----------------------------------------------------------------------------------------------------------------------
  区域                    当前职责                主要内容
  ----------------------- ----------------------- ----------------------------------------------------------------------
  顶部栏                  品牌、状态和全局操作    项目名称、Python/课程/schema/辅导模式/运行状态、学习总结、保存、打开

  启动检查区              环境准备和异常提示      启动检查结果、重试、进入课堂

  工具箱                  提供可用积木            积木列表、分类与拖放

  积木画布                核心编辑区域            Canvas、拖放与连接、空状态提示、Python 代码预览

  课程区                  课程和任务说明          学习目标、任务卡片、完成标准、预测问题、后续主题

  运行控制区              执行程序                运行、停止、重置、舞台和角色状态

  结果区                  呈现运行结果            运行反馈、输出、预测对照

  辅导区                  提供 AI 教学支持        辅导回复、提示等级选择、自由提问

  总结区                  回顾学习过程            本次会话总结、变式练习和结束入口
  ----------------------------------------------------------------------------------------------------------------------

目前页面同时呈现较多功能区域。对于熟悉系统的开发者，这种布局便于观察完整链路；对于初次使用的儿童，可能需要同时理解多个区域及其关系。

### 2.2 已有布局规则

当前 `frontend/css/app.css` 主要采用以下布局：

-   **宽度不小于 1280px：**
    三列布局，编辑器位于左侧，课程区位于中间，运行控制和辅导区位于右侧，结果区位于编辑器下方。
-   **宽度小于 1280px：**
    两列布局，编辑器占据左侧较大区域，课程区位于右侧，运行控制、结果和辅导区域向下排列。
-   **宽度小于 1024px：** 单列排列，并显示最低窗口尺寸提示。
-   编辑器内部再分为工具箱和画布，当前默认工具箱宽度约为
    170px，在较窄布局下调整为 140px 或 130px。
-   编辑器所在行设置了 `minmax(420px, auto)`，结果所在行设置了
    `minmax(220px, auto)`。

这些规则已经提供了基础响应式能力，但断点较少，主要依据宽度切换，没有充分考虑窗口高度、浏览器缩放、不同面板内容增长和工作区实际可用面积。

### 2.3 当前值得优先处理的问题

#### A. 功能区域较多，视觉主次不够明确

页面上同时存在状态栏、启动检查、课程区、编辑区、运行控制、结果区和辅导区。每个区域都有独立标题、边框、背景和说明文字，容易形成"多个面板同等重要"的视觉效果。

其中，顶部状态栏中的 Python 版本、课程/schema
版本和辅导模式等信息主要服务于开发、调试和演示环境检查，对儿童当前的学习操作帮助有限，长期固定展示会占据注意力和横向空间。

#### B. 课程区承担了过多信息

当前课程视图可能同时展示学习目标、多个任务卡片、完成标准、预测问题和后续主题。孩子在当前任务中真正需要的信息通常只有：

-   当前任务是什么；
-   要完成什么目标；
-   当前应该做哪一步；
-   怎样判断本次任务完成。

其余内容可以按需展开，不宜与当前任务并列展示。

#### C. 运行、结果和辅导的关系可以更紧密

运行控制、结果和 AI
辅导被分成不同面板。孩子需要在不同区域之间寻找"运行后发生了什么""为什么没有成功""接下来该怎么改"。

建议将运行结果和辅导建议组织为一个连续反馈流程：**运行 → 观察结果 →
查看提示 → 修改程序 → 再次运行**。

#### D. 工作区空间分配仍有优化余地

积木画布是产品最核心的操作区域，应优先获得可用空间。工具箱、代码预览和课程说明都应服务于画布，而不应长期挤压画布宽度。

当前编辑器面板内部固定保留工具箱列，代码预览也在画布下方常驻。对于低高度窗口或较复杂程序，可能需要重新安排工具箱和代码预览的显示方式。

#### E. 窗口高度和缩放场景需要单独设计

当前布局的主要断点为 1280px 和 1024px，且编辑器和结果行有最小高度。对于
1280×720
这类常见笔记本窗口，顶部栏、启动区、主工作区最小高度和面板间距叠加后，容易产生较多纵向滚动。

应将窗口高度、浏览器缩放比例和面板内部滚动纳入正式验收，而不能只检查页面宽度。

## 3. 建议一：以成熟开源项目作为 UI/UX 参考基线

### 3.1 参考原则

"直接参考成熟项目"应具体落实为对成熟界面模式的复用，而不是只模仿配色或圆角。

建议每次参考都回答以下问题：

1.  该项目如何安排课程说明、工具箱、工作区和运行结果？
2.  页面如何突出当前任务和主要操作？
3.  积木拖动、插入、删除、运行和报错时分别如何反馈？
4.  面板在窄窗口、低高度窗口下如何折叠、移动或隐藏？
5.  哪些交互已经经过大量儿童用户验证，适合直接借鉴？
6.  哪些设计依赖其自身的课程体系或运行环境，不适合照搬？

优先复用经过验证的交互范式和组件结构；只有在现有实现确实无法满足需求时，才考虑重新设计。

### 3.2 建议重点研究的项目

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  参考项目                                           重点观察内容                                                   对 CodeMateKids 的借鉴价值
  -------------------------------------------------- -------------------------------------------------------------- ------------------------------------------------------------------
  [Scratch](https://scratch.mit.edu/)                积木分类、积木形状与语义、舞台与工作区关系、角色反馈           建立儿童对积木、程序和运行结果之间关系的直观认识

  [Code.org Sprite                                   课程指引、舞台、工具箱、工作区的分区方式；逐步开放可用积木     适合参考小学阶段的任务引导和低认知负担布局
  Lab](https://code.org/tools/sprite-lab)                                                                           

  [Microsoft MakeCode](https://makecode.com/)        模拟器、工具箱、工作区的布局；运行控制；积木与代码视图切换     适合参考编程工作台的空间组织、运行反馈和渐进式功能展示

  [Blockly](https://developers.google.com/blockly)   工具箱、工作区、积木连接、插入提示、键盘操作和工作区布局建议   与当前自研积木编辑器最接近，可作为编辑器交互和布局的重要技术参考
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

建议优先研究 Code.org Sprite Lab 和 MakeCode 的完整教学操作流程，再用
Blockly 文档核对积木工作区的专业交互细节。

### 3.3 具体复用范围

#### 页面布局

-   参考成熟产品的主工作区分区，不再为每个功能单独创建同等权重的卡片。
-   将课程任务说明、积木工具箱、编辑工作区和运行预览组织成稳定的主操作区域。
-   保证工作区始终是视觉中心，且随窗口变化优先扩展。
-   低频内容使用抽屉、弹层、折叠区或标签页承载，避免永久占据主界面。

#### 视觉组件

优先统一以下组件的样式和状态：

-   主按钮、次按钮、危险按钮和禁用按钮；
-   面板标题、任务卡片、步骤提示和状态标签；
-   积木工具箱分类、积木列表项和拖放预览；
-   输入框、参数槽、提示气泡和确认弹窗；
-   成功、错误、警告、加载和空状态；
-   Toast、运行进度、结果摘要和 AI 回复气泡。

建议先建立一套全局组件规范，再批量替换页面中重复且不一致的样式，避免每个模块各自定义按钮、边距和颜色。

#### 交互反馈

重点参考成熟产品的以下行为：

-   拖动积木时，明确显示当前拖动对象和可放置位置；
-   合法位置与非法位置有明显区别；
-   插入、连接和嵌套时显示结构变化预览；
-   拖放失败时恢复原状，并说明原因；
-   运行时提供清晰的运行中状态，必要时高亮当前执行积木；
-   运行结束后立即呈现关键结果和下一步操作；
-   保存成功、保存失败、作品未保存等状态有明确反馈；
-   操作成功后给予简短、积极、不过度打断的反馈。

### 3.4 复用策略与技术边界

当前 CodeMateKids 已有自研 Canvas
积木编辑器，包含程序模型、拖放、连接、撤销/重做、运行高亮和无障碍语义镜像等能力。建议采用分层复用策略：

1.  **优先复用设计与交互模式：**
    先借鉴成熟产品的布局、按钮、面板、拖放反馈和提示方式。
2.  **其次复用成熟组件或库：** 如果 Blockly
    的现有能力能满足后续需求，应评估直接采用其工具箱、工作区或辅助交互的成本。
3.  **谨慎决定是否替换编辑器内核：** 若要从自研 Canvas 迁移到
    Blockly，需要单独评估程序数据模型、课程积木定义、Python
    生成、保存格式、键盘交互、运行事件和现有测试的迁移成本。
4.  **保持业务逻辑稳定：** 视觉重构不应顺带改变课程协议、运行器、AI
    辅导策略、学习证据和作品保存格式。
5.  **遵守许可证和资产授权：**
    引入开源代码或组件前，核对许可证、版本、依赖和二次分发要求；可以借鉴交互，但不要直接复制未获授权的品牌图形、角色、插画或专有素材。

**建议决策：本轮先完成 UI
模式复用和组件统一，不把"重写积木编辑器"作为默认任务。**

## 4. 建议二：降低信息密度，让儿童始终聚焦当前任务

### 4.1 设计目标

面向小学三年级及以上儿童，界面应尽量做到：

-   一屏突出一个当前学习目标；
-   一个时刻突出一个主要操作；
-   一段说明只表达一个核心要求；
-   运行后优先显示最重要的结果；
-   复杂信息按需展开，不默认全部展示。

页面不需要展示系统拥有的全部能力。儿童在当前步骤中需要的信息才应该占据主要视觉位置。

### 4.2 重新定义信息优先级

建议将页面信息划分为三级：

  -----------------------------------------------------------------------------------------------------------------------------
  层级                    信息类型                                                     展示方式
  ----------------------- ------------------------------------------------------------ ----------------------------------------
  P0：当前必须看到        当前任务、操作目标、积木工作区、主要操作按钮、关键运行结果   默认直接展示，位置稳定，视觉突出

  P1：当前可能需要        轻提示、完成标准、运行细节、代码预览、撤销/重做、任务进度    以紧凑卡片、标签页或可展开区域展示

  P2：低频或技术信息      Python/schema                                                收纳到"更多信息""系统状态"或开发模式中
                          版本、调试信息、详细执行日志、后续课程列表、开发诊断         
  -----------------------------------------------------------------------------------------------------------------------------

### 4.3 页面各区域的具体改造

#### A. 顶部栏：只保留儿童常用入口

建议默认保留：

-   产品标识；
-   当前课程/任务进度；
-   保存状态；
-   一个简洁的帮助或菜单入口。

建议将以下内容移出儿童主视图：

-   Python 版本检查；
-   schema 版本；
-   详细运行状态；
-   mock/真实模型模式等技术标识；
-   不常用的开发诊断信息。

这些信息可以放入"系统信息"弹层或开发模式。若演示确实需要展示"演示回复"模式，可以保留一个低强调度的简短标记，不应与课程标题和主要操作争夺注意力。

保存和打开作品可以保留，但建议合并到"作品"菜单或更多操作中，减少顶部按钮数量。

#### B. 课程区：只突出当前任务

建议课程区默认展示：

1.  当前课程名称和简短进度；
2.  当前任务标题；
3.  一句明确的任务目标；
4.  一条必要的完成标准；
5.  当前步骤或预测问题。

以下内容建议默认折叠：

-   全部学习目标列表；
-   尚未开始的其他任务卡片；
-   后续课程主题；
-   较长的完成条件解释；
-   与当前任务无关的教学背景。

课程任务切换可以通过"上一步/下一步"或简洁任务导航完成。不要让多个任务卡片同时占据课程区主体。

#### C. 工具箱：让孩子快速找到要用的积木

建议：

-   优先展示当前任务允许使用的积木；
-   积木类别数量较少时直接展示，不再增加多层分类；
-   类别较多时使用清晰的图标和短标签；
-   每个积木项优先展示名称和必要的图形示例；
-   积木说明在悬停、选中或点击后出现；
-   暂不可用的积木默认隐藏，确有教学价值时再以锁定状态展示，并说明解锁条件。

不要在工具箱中同时展示大量暂时无法使用的积木，否则会让孩子误以为这些积木也是当前任务必须掌握的内容。

#### D. 积木画布：成为页面的视觉中心

建议：

-   画布占据主内容区最大面积；
-   默认保留必要的缩放、居中和撤销/重做操作；
-   空画布只显示一句开始提示，并可用轻量示意说明拖放方式；
-   选中积木时显示清晰边框或局部工具栏；
-   参数编辑尽量直接发生在积木内部；
-   代码预览默认折叠，用户主动打开后再显示；
-   画布缩放和窗口尺寸变化时，Canvas
    的实际绘制尺寸、坐标换算和鼠标命中位置必须同步更新。

#### E. 运行与结果：合并为连续的反馈体验

建议将运行控制和结果区整合为一个"运行与结果"区域：

-   默认突出"运行"按钮；
-   运行中将主按钮切换为明确的运行状态，并提供"停止"；
-   "重置"作为次级操作，不与"运行"保持同等视觉权重；
-   运行结束后先显示一句结果摘要；
-   需要时再展开输出内容、预测对照和执行细节；
-   错误反馈应说明"发生了什么"和"可以尝试什么"，避免展示面向开发者的堆栈、路径或内部错误码。

预测对照可以用简短的"你猜的 /
实际发生的"呈现，不必默认显示多行技术数据。

#### F. AI 辅导：从多个按钮转向明确的下一步

当前辅导区同时提供轻提示、更多提示、换个例子、自己试、跳过和自由提问等入口。建议根据当前状态动态显示操作：

-   初始状态：突出"给我一点提示"；
-   已给出提示：突出"我再试试"，次级提供"再给一点提示"；
-   多次尝试失败：提供"换个例子"或"分步骤讲解"；
-   孩子主动需要帮助时：保留自由提问入口；
-   "跳过"放在次级菜单或低强调度位置。

AI
回复默认只展示当前最有帮助的一段内容。详细解释、依据和扩展示例可以折叠展开。

辅导语言应简短、具体、积极，优先给出下一步行动。例如："试着把重复的动作放进循环里。"比一段完整的技术概念解释更适合作为第一次提示。

#### G. 学习总结：减少评价感，突出具体收获

总结页建议突出：

-   今天完成了什么；
-   本次练习中观察到的一个具体进步；
-   可以继续尝试的一个小挑战。

继续保持现有原则：不使用分数、排名和永久能力标签；总结明确限定为本次会话观察，不将一次练习结果描述成长期能力结论。

### 4.4 儿童界面的文案与视觉原则

-   优先使用儿童熟悉的动词，如"开始""试一试""看看结果""再改一改"。
-   一条提示尽量控制在 1～2 句，先说动作，再解释原因。
-   少用抽象术语；确实需要引入术语时，配合图形或具体例子。
-   主要按钮使用"动作 + 结果"式文案，例如"运行程序""保存作品"。
-   图标必须配合文字，不能只依赖图标猜测功能。
-   避免同时使用过多高饱和颜色、装饰插画、动画和徽章。
-   成功反馈应积极但克制，避免频繁弹窗、长动画或强制等待。

## 5. 建议三：优化窗口适配与空间利用率

### 5.1 布局重构目标

建议把当前多个平级面板重组为三个主要工作区域：

1.  **任务区：** 当前任务、目标、必要步骤和进度。
2.  **编辑区：** 工具箱与积木画布，是页面的主要区域。
3.  **运行区：** 舞台/运行结果，以及按需打开的 AI 辅导。

在宽屏下，三个区域同时可见；在较窄窗口下，任务区和运行区可以折叠为侧栏或抽屉，编辑区优先保留。

一个可供讨论的桌面布局：

``` text
┌─────────────────────────────────────────────────────────────┐
│ 品牌 / 当前课程与进度                         作品 / 帮助    │
├────────────┬──────────────────────────────┬─────────────────┤
│            │                              │                 │
│ 当前任务   │  工具箱  │   积木工作区       │  舞台 / 结果    │
│            │          │                    │                 │
│ 目标       │  积木    │   拖放、连接、编辑  │  运行反馈      │
│ 步骤       │  分类    │                    │                 │
│            │          │                    │  AI 提示入口   │
│            │          │                    │                 │
├────────────┴──────────────────────────────┴─────────────────┤
│ 运行 / 停止 / 撤销 / 重做等与当前状态相关的操作              │
└─────────────────────────────────────────────────────────────┘
```

该示意图用于表达信息关系，不要求逐像素照搬。若实际窗口高度有限，可以把底部操作栏放入编辑区顶部，避免浪费纵向空间。

### 5.2 建议的响应式策略

  ---------------------------------------------------------------------------------------------------------------
  场景                    建议布局                 重点要求
  ----------------------- ------------------------ --------------------------------------------------------------
  ≥1440px 宽              三个主要区域同时展示     编辑区最大；任务区和运行区保持稳定宽度

  1200～1439px            三栏紧凑布局             减少侧栏宽度；代码预览、详细结果和辅导内容默认折叠

  1024～1199px            编辑区优先，侧栏可折叠   任务区可收为窄栏；运行区使用标签页或抽屉

  \<1024px                单列或分步视图           不强行压缩三栏；明确提示窗口较窄，优先保证编辑和运行流程可用

  高度 ≤720px             紧凑工作台               减少顶部占高；面板内部滚动；不设置过大的固定最小高度
  ---------------------------------------------------------------------------------------------------------------

建议以 1024×768 作为本轮最低桌面验收基线，并至少检查 1280×720、1366×768
和
1440×900。若后续决定支持平板或触屏，应另行制定触控布局与拖放验收规范。

### 5.3 空间分配建议

以下数值作为首轮设计参考，最终以真实窗口测试和可用性观察为准：

-   顶部导航栏高度控制在约 52～60px；
-   任务侧栏宽度约 200～240px；
-   工具箱宽度约 150～180px；
-   运行/预览侧栏宽度约 240～300px；
-   中央画布始终使用 `minmax(0, 1fr)`，优先获得剩余空间；
-   面板外间距以 8～12px 为主，避免大面积无效留白；
-   面板内部边距以 10～14px 为主；
-   主要操作按钮高度建议不低于 40～44px；
-   儿童主要阅读文本建议使用 14～16px，辅助说明不宜过小。

不建议给所有面板设置固定高度。优先使用
`min-height: 0`、`min-width: 0`、`minmax(0, 1fr)`
和明确的内部滚动容器，避免内容增长时撑破整个网格。

### 5.4 高度适配和滚动规则

-   页面整体只保留必要的纵向滚动，避免多个区域同时出现滚动条。
-   画布容器应占据可用高度，工具箱和右侧结果区可以独立滚动。
-   低高度窗口下，启动检查结果应收起为状态入口，不应长期占据主工作区上方。
-   代码预览、详细运行日志和辅导历史应按需展开。
-   主要操作按钮在编辑区内保持容易找到的位置。
-   Canvas
    尺寸变化时必须同步处理像素尺寸、缩放比例、绘制坐标和指针命中坐标。
-   适配浏览器 100%、125% 和 150% 缩放，避免只在 100% 下布局正常。

### 5.5 技术实现建议

-   将断点从单纯的宽度判断升级为"宽度 + 高度 + 面板状态"的组合策略。
-   使用 CSS Grid/Flex 实现主要布局，不通过大量绝对定位拼接面板。
-   统一面板的尺寸变量、间距变量和折叠状态。
-   对工具箱、任务区、运行区的展开/收起状态建立明确状态管理，避免 DOM 和
    CSS 状态不一致。
-   为 Canvas 增加尺寸变化监听；尺寸变化后重新计算画布和命中区域。
-   优先使用 CSS `minmax(0, 1fr)`，避免 Grid
    子项的默认最小内容宽度导致横向溢出。
-   页面需要适应高度变化时，优先使用 `100dvh`
    或合理的视口高度计算，同时保留内容不足时的自然滚动。

## 6. 交互状态规范

建议建立统一的状态反馈规范，避免不同模块各自实现相似交互。

  场景            必须提供的反馈           建议形式
  --------------- ------------------------ --------------------------------------
  普通按钮悬停    明确可点击               轻微背景变化或边框变化
  键盘聚焦        明确当前焦点             清晰可见的焦点描边
  按钮按下        明确操作已触发           轻微按压反馈
  禁用操作        说明当前不可操作的原因   禁用样式 + 必要的短说明
  积木拖动中      明确正在移动的对象       拖动预览、半透明原件或影子
  合法放置位置    明确可以放置             插入线、吸附轮廓或结构预览
  非法放置位置    明确不能放置             禁止符号/形状差异 + 简短原因
  拖放失败        明确操作未生效           恢复原结构，不留下半连接状态
  程序运行中      明确运行状态             运行按钮状态变化、进度提示、执行高亮
  程序运行成功    明确结果和下一步         结果摘要 + 继续修改/尝试变式
  程序运行失败    说明问题和可尝试动作     友好错误说明 + 定位到相关积木
  保存成功/失败   明确保存结果             Toast 或状态文字
  内容加载中      避免误认为页面无响应     局部加载状态，不阻塞无关区域
  无内容          告诉孩子从哪里开始       一句短说明 + 主要入口

### 6.1 交互一致性要求

-   相同语义的按钮在不同区域使用相同颜色、尺寸和反馈方式。
-   成功、警告、错误状态不能只靠颜色区分，还应有文字、图标或形状差异。
-   动画只用于说明状态变化，不作为装饰性负担；尊重减少动态效果的系统设置。
-   错误信息优先解释用户可以采取的下一步。
-   重要操作要防止重复提交，状态变化要及时反映在界面上。
-   所有主要功能保留键盘可达路径，拖放操作应提供合理的键盘替代方式。

## 7. 设计系统与组件统一

建议先建立轻量设计系统，不必一次性引入大型 UI 框架。

### 7.1 基础设计变量

建议采用统一的设计变量，具体颜色和尺寸在参考项目对比后确定：

  类型     建议规范
  -------- --------------------------------------------------------------
  字体     中文优先使用系统易读字体；正文 14～16px，说明 12～14px
  间距     以 4px 为基础单位，常用 8/12/16/24px
  圆角     小控件 8～10px，主要面板 12～16px
  边框     使用低对比度中性色，减少每个区域的强边框感
  主色     统一用于主要操作和当前选中状态
  成功色   仅用于成功、完成等明确状态
  警告色   用于等待、提醒和需要注意的状态
  错误色   用于失败、危险操作和明确错误
  阴影     只用于有层级关系的浮层或重要面板，避免所有卡片都使用明显阴影

### 7.2 组件清单

首轮建议统一以下组件：

-   `AppHeader`：顶部导航和全局操作；
-   `SystemStatus`：开发/演示模式下的系统状态；
-   `TaskPanel`：当前任务和步骤；
-   `Toolbox` / `ToolboxItem`：积木分类与积木项；
-   `WorkspaceToolbar`：画布操作；
-   `BlockCanvas`：积木工作区；
-   `RunControls`：运行、停止和重置；
-   `RunResult`：结果摘要、输出和错误定位；
-   `TutorPanel`：提示、追问和下一步行动；
-   `Toast`、`Dialog`、`EmptyState`、`LoadingState`：全局反馈组件。

组件统一后，优先通过变量和组件属性调整视觉，而不是在每个页面中单独维护大量重复
CSS。

## 8. 实施顺序与任务拆分

建议分阶段改造，先解决影响最大的问题，再做细节美化。

### P0：参考分析与现状盘点

**目标：** 明确要借鉴什么、保留什么、先改什么。

-   [ ] 对 Scratch、Code.org Sprite Lab、MakeCode、Blockly 各选取 2～3
    个关键页面或交互状态。
-   [ ]
    记录页面分区、主次按钮、工作区占比、拖放反馈、运行反馈和响应式行为。
-   [ ] 对 CodeMateKids 当前页面进行截图和问题标注，至少覆盖
    1280×720、1024×768。
-   [ ] 建立组件清单和当前样式清单。
-   [ ] 明确本轮保留自研 Canvas 编辑器，不默认启动编辑器内核迁移。
-   [ ] 确认本轮设计的最低支持窗口和浏览器范围。

**交付物：** 参考项目对比表、当前页面问题清单、目标布局草图。

### P1：全局布局与设计系统

**目标：** 先统一视觉语言和空间框架。

-   [ ] 统一字体、颜色、间距、圆角、阴影和按钮尺寸。
-   [ ] 重构顶部栏，减少儿童主视图中的技术状态信息。
-   [ ] 调整主页面 Grid，将任务区、编辑区和运行区明确分层。
-   [ ] 优先扩大中央画布，压缩低频区域。
-   [ ] 增加面板折叠、展开和窄窗口状态。
-   [ ] 处理 1280×720 下的垂直空间问题。

**交付物：** 全局 CSS 变量、主页面布局、基础组件样式。

### P2：儿童信息架构与内容呈现

**目标：** 降低同时呈现的信息量。

-   [ ] 课程区默认只展示当前任务。
-   [ ] 学习目标、后续主题和其他任务改为按需展开。
-   [ ] 代码预览和详细运行输出默认折叠。
-   [ ] 将运行结果与 AI 辅导组织成连续反馈流程。
-   [ ] 根据当前状态动态调整辅导按钮，减少同时出现的选择项。
-   [ ] 统一儿童文案，确保主要操作一眼可理解。

**交付物：** 课程区、结果区和辅导区的新版信息结构。

### P3：交互反馈与状态统一

**目标：** 让每次操作都有清晰、一致、可恢复的反馈。

-   [ ] 统一按钮 hover、focus、active、disabled 状态。
-   [ ] 统一积木拖动、合法放置、非法放置和失败回滚反馈。
-   [ ] 统一运行中、成功、失败、停止和断线恢复状态。
-   [ ] 统一保存、加载、切换任务和未保存修改提示。
-   [ ] 检查键盘焦点顺序、快捷键提示和非颜色状态区分。
-   [ ] 检查动画是否会干扰操作或造成等待。

**交付物：** 交互状态规范和对应实现。

### P4：响应式验收与回归

**目标：** 保证 UI 改造不破坏现有教学闭环。

-   [ ] 检查所有目标分辨率和浏览器缩放比例。
-   [ ] 检查 Canvas 缩放、拖放命中、积木连接和撤销/重做。
-   [ ] 检查预测、运行、结果、AI 辅导、修改、变式和总结全流程。
-   [ ] 检查运行中停止、断线恢复、作品保存/打开和任务切换。
-   [ ] 执行现有 pytest 与前端 Node 检查。
-   [ ]
    记录真实浏览器检查结果；自动化逻辑测试不能替代真实浏览器布局与拖放验收。

**交付物：** UI 改造验收记录、问题清单和回归结果。

## 9. 验收标准

### 9.1 视觉与信息层级

-   [ ]
    首次进入课堂时，儿童能够快速识别当前任务、积木画布和主要操作入口。
-   [ ] 默认视图中只有一个明确的主要操作按钮。
-   [ ] 技术诊断信息不会与学习任务争夺视觉注意力。
-   [ ] 课程区默认只突出当前任务，其他任务和扩展内容按需展开。
-   [ ] 代码预览、详细输出和辅导历史不会长期占据主工作区。
-   [ ] 同类组件在不同页面中的颜色、尺寸、边距和状态保持一致。

### 9.2 窗口适配

至少覆盖以下分辨率：

  分辨率     验收重点
  ---------- ----------------------------------------------------
  1440×900   三个主要区域完整展示，编辑区空间充足
  1366×768   主要操作不被遮挡，页面无横向溢出
  1280×720   顶部和启动区不过度占高，画布仍可有效编辑
  1024×768   侧栏可折叠或切换，核心编辑与运行流程可完成
  \<1024px   给出明确的窄窗口提示或进入简化布局，不出现内容重叠

同时检查 100%、125%、150% 浏览器缩放。

### 9.3 交互与教学闭环

-   [ ] 工具箱添加、拖动、插入、嵌套和删除积木均有明确反馈。
-   [ ] 非法拖放不会破坏程序结构。
-   [ ] 运行、停止、重置状态明确，重复点击不会造成重复提交。
-   [ ] 运行结果能够引导孩子完成下一步修改。
-   [ ] AI 提示与当前任务和程序状态相关，且不会默认直接替孩子完成任务。
-   [ ] 键盘路径可完成主要操作，焦点状态清晰。
-   [ ] UI 改造不改变程序模型、课程协议、运行安全边界和作品兼容性。

### 9.4 性能与可用性

-   [ ] 拖动、吸附、选中和撤销等高频交互保持流畅；沿用当前项目 P95
    ≤100ms 的交互响应目标进行测量。
-   [ ] Canvas 尺寸变化后，绘制、缩放和指针命中保持一致。
-   [ ] 面板展开/收起不造成明显布局抖动。
-   [ ] 页面不存在横向滚动条、面板重叠、内容被裁切或按钮无法点击等问题。
-   [ ]
    真实浏览器验收记录包含浏览器版本、操作系统、分辨率、缩放比例和输入设备。

## 10. 改造时需要保护的现有能力

UI 改造应尽量限定在视图层和样式层，以下能力应作为回归保护范围：

-   自研积木程序模型、积木连接规则和课程积木定义；
-   Canvas 绘制、坐标换算、拖放、吸附、插入和嵌套；
-   撤销/重做和作品保存/打开；
-   Python 代码生成与受约束运行器；
-   运行事件、执行高亮、停止和断线恢复；
-   预测、课程切换、任务状态和变式任务；
-   AI 辅导分层策略和学习证据链；
-   键盘操作与无障碍语义镜像；
-   当前 API、schema、课程版本和作品格式兼容性。

如果 UI
结构调整需要修改上述模块，应先明确接口变化和回归范围，不应把视觉改造与核心逻辑重写混在同一个改动中。

## 11. 最终建议

建议本轮按照以下顺序推进：

1.  **先参考成熟项目确定目标布局和组件规范。** 优先研究 Code.org Sprite
    Lab、MakeCode 和 Blockly 的工作区组织方式及交互反馈。
2.  **再重构页面信息层级。**
    儿童默认只看到当前任务、主要编辑区域和当前反馈；技术状态与扩展内容按需显示。
3.  **最后集中处理窗口适配。** 重点验证 1280×720 和
    1024×768，确保中央画布获得足够空间，低高度窗口不会因固定面板高度产生拥挤。

本轮 UI
改造的完成标志，不是页面增加了多少装饰或组件，而是孩子能够更快找到当前任务、更顺畅地完成积木编辑，并且在运行后立即理解结果和下一步应该做什么。
